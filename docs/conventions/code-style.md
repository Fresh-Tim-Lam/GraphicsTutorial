# code-style.md — 代码风格规范

> **用途**：规定本仓库 C++ 代码的书写风格约定（当前聚焦**类定义内的成员组织顺序**），使类"先见内部状态、后见对外接口"，降低阅读与维护成本。
> **目标读者**：编写/修改 `src/include/gfx/` 及教程示例 C++ 代码的开发者与 AI Agent。
> **关联文档**：[naming.md](naming.md)（命名与语言习惯）；[api-docs.md](api-docs.md)（公共接口注释规范）；[performance.md](performance.md)（性能敏感写法）；[meta-rules.md](meta-rules.md)（规范元规则：场景前缀与状态标记）。

> 状态：生效中（核验于 2026-10-06）。

## 规则

### 1. [类定义组织] ✅ 采纳（2026-10-06）

- **规则**：同一个类定义内，**`private:` 段置于 `public:` 段之前**（成员声明在前、对外接口在后）；即先把数据成员（类的"状态/不变式"）写在前面，再写对外接口（成员函数/公开访问器）。
- **理由**：读者打开类定义时，先看到**数据成员与不变式**（该类持有/维护什么状态、有哪些约束），再看**对外接口**（能对它做什么）。先"状态"后"行为"符合"先看清对象是什么、再看能对它做什么"的阅读顺序，便于快速把握类的状态与职责边界。
- **例外**：以下情形**不必强求**（可保持 public 在前或按自然顺序书写）：
  1. 类很小（仅 1–2 个成员），顺序对可读性影响可忽略；
  2. 纯接口 / 无状态类型：仅有 `static` 工具函数的工具类、`enum class`、tag 类型等（无数据成员，无 `private:` 段可言）；
  3. 纯数据载体（如聚合 `struct`）：`public` 数据即全部接口，无"内部实现"可前置；
  4. 若私有成员（或私有函数签名）的类型依赖的嵌套类型本身是**对外公开 API**（被类外引用），
     则**不得**为满足"private 在前"而将其私有化；此时允许写成
     `public:`（仅该公开类型）→ `private:`（数据成员）→ `public:`（其余接口）的分段形式
     （落点：`src/include/gfx/render/window.hpp` 的 `Window::Impl`）。
- **迁移落点**：
  - 调整既有类时**只做"段顺序调整 + 注释原样搬运"**，不改动成员的名字/类型/初值/注释内容，也不改任何函数实现；
  - 若私有数据成员的**类型依赖某个嵌套类型**（如 `std::vector<Edge> edges_;` 依赖同类的 `struct Edge`），该嵌套类型须**随数据成员一并前移**（C++ 要求"先声明后使用"，同段内 `Edge` 必须先于 `edges_`），并归入内部实现（`private:`）一侧。
- **落点示例**：`src/include/gfx/render/raster.hpp` 的 `ScanlineFiller` —— `private:`（边表条目 `Edge` 与数据成员）前移，`public:`（`begin` / `step` / `fillCurrentRow` 及访问器）随其后。
